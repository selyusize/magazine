# План бэкенда (Medusa 2) — Snowaa Dropshipping

**Snowaa Dropshipping** — сеть SEO-ориентированных дропшиппинг-магазинов на одном бэкенде. Каждый магазин — свой
фронтенд (отдельный репозиторий, свой домен и дизайн), свои поставщики, товары, категории, бренды, характеристики,
статьи, текстовые блоки, посадочные, редиректы, SEO, фиды. Общее на всю сеть: покупатели (логин, профиль, адреса,
история заказов), способы доставки и оплаты, юрлицо и юридические документы, промокоды сети, бонусный счёт, отзывы
о сервисе сети.

Контекст: Medusa 2.21, рынок РФ (RUB, НДС, ЮKassa/СБП, СДЭК, 54-ФЗ, 152-ФЗ), self-hosted Docker, всё
разворачивается **только через Ansible**. Фронты рендерят страницы и sitemap сами, бэкенд отдаёт данные. Масштаб на
год: 10–50 магазинов, до 1 млн товаров. Первый магазин — **olisa** (фронт в этом репозитории, `frontend/`),
остальные фронты — в своих репозиториях. Трафик покупается в таргетированной рекламе (Яндекс Директ, VK Реклама),
поэтому SEO, скорость посадочных, товарные фиды и учёт конверсий — главный приоритет.

Модель бизнеса — **дропшиппинг**: склада нет. Каталог, закупочные цены и остатки приходят от поставщиков в
**CommerceML 2**, заказы уходят поставщику, он и отгружает.

## Как читать план

- Шаги идут строго по порядку, **один шаг — одна сессия**. Шаг закрыт, когда выполнено «Готово, когда» и
  зелёные `pnpm lint`, `tsc`, `pnpm test:unit`, `pnpm test:integration:http` (на фронте — `lint`, `lint:fsd`,
  `typecheck`, `test`).
- В начале сессии: прочитать шаг, `backend/arch-guide.md`, код, который шаг меняет, и пример из
  [medusajs/examples](https://github.com/medusajs/examples), если он указан у шага.
- В конце сессии отметить шаг ✅ с датой и коротко записать, что сделано и что перенесено (с номером шага, куда
  перенесено).
- **Бэкенд в режиме разработки: любые данные можно удалять.** БД, `backend/static`, `backend/exchange`,
  `backend/logs`, Redis, индекс поиска удаляются и поднимаются заново в любой момент, ничего не сохраняем и не
  переносим. Поэтому миграции и сид правим на месте (не пишем корректирующие миграции и скрипты переноса данных),
  схему меняем как удобно, а после шага с изменением схемы просто пересоздаём БД и запускаем сид. Правило
  действует до запуска olisa (шаг 45); после релиза — только новые миграции и перенос данных.

## Ключевые решения по мультимагазину

| Вопрос | Решение |
| --- | --- |
| Что такое магазин | Модуль `shop` (slug, название, домен, URL витрины, настройки) + связь 1:1 с **sales channel** Medusa. У магазина свой publishable key |
| Как бэкенд узнаёт магазин | Store API: по publishable key (ключ → один sales channel → магазин), `req.shop`. Admin API: заголовок `x-shop-id` от переключателя магазина в админке |
| Товары | **Свои у каждого магазина**: товар состоит ровно в одном sales channel. Поставщик принадлежит одному магазину, поэтому импорт создаёт товары в его магазине; склейка дублей по штрихкоду идёт только внутри магазина |
| Handle сущностей Medusa (товар, категория, коллекция) | В Medusa handle уникален глобально, поэтому хранится с префиксом магазина `olisa--utyug-philips`. Наружу (store API, пути, sitemap, фиды) отдаётся без префикса. Slug уникален внутри магазина |
| Свои сущности (бренд, характеристика, статья, текстовый блок, посадочная, редирект, SEO, фид) | Поле `shop_id`, уникальность handle/path — по паре `(shop_id, …)`, индексы начинаются с `shop_id` |
| Категории | Своё дерево у каждого магазина: связь `product_category ↔ shop`. Основная категория, бренд и характеристики товара — только из его магазина |
| Покупатели | Общие (как в Medusa). Один логин, профиль и адреса на все магазины. «Мои заказы» показывают заказы всех магазинов с пометкой, из какого магазина заказ |
| Корзина и заказ | Свои у каждого магазина (корзина живёт в sales channel). Внутри заказа — разбиение по поставщикам |
| Доставка | Один набор способов и договоров (СДЭК, Яндекс). Магазин включает или выключает способы и задаёт порог бесплатной доставки |
| Оплата | Одно юрлицо, свой **shopId ЮKassa на магазин**. Провайдер один, ключи берёт из настроек магазина заказа |
| Юрдокументы и согласия | На сеть (одно юрлицо): оферта, политика ПДн, согласие. В согласии записывается, в каком магазине его дали |
| Письма | От магазина: свой отправитель, логотип и ссылки. Сброс пароля ведёт на сайт, с которого его запросили |
| Промо и бонусы | Промокод на сеть (без условия) или на магазин (условие по `sales_channel_id`). Бонусный счёт общий: баллы копятся и тратятся в любом магазине |
| Отзывы | О товаре — у товара, то есть у магазина. О сервисе — на сеть |
| Создание магазина | Кнопкой в админке: магазин, sales channel, publishable key, корневая категория, настройки по умолчанию. Деплой бэкенда не нужен; фронт магазина — запись в inventory Ansible и одна команда |
| Админка | Одна. Переключатель текущего магазина, все свои разделы фильтруются по нему. Ограничение менеджеров по магазинам — отдельный шаг в конце |
| Кэш | Любой кэш (бэкенд и витрина) сбрасывается **по событию изменения**, а не только по времени. TTL — страховка, а не механизм обновления |
| Инфраструктура | Имя сети `snowaa`: контейнеры `snowaa-backend`, `snowaa-postgres` и т. д., фронты — `<магазин>-frontend` (`olisa-frontend`). Деплой, миграции, бэкапы, логи, разовые команды — playbook'и Ansible и цели `make`, без захода на сервер |

## Сквозные правила

**Архитектура.**

- Всё — по `backend/arch-guide.md`: Action → Handler (command, workflow со steps и откатом) / Fetcher (query),
  `entity/` + реэкспорт в `models/`, DTO у своего use-case, zod-схемы, зависимости через `src/container`, без `as`.
- Новый кастомный роут — с блоком `@oas`, затем `pnpm openapi:generate` → Orval на фронте olisa. Внешние фронты
  берут ту же спеку (шаг 25).
- **Любой store-роут работает в рамках `req.shop`**, любой admin-роут своих сущностей — в рамках текущего магазина.
  Каждая новая сущность получает `shop_id` (или явно помечена как сетевая).
- Тяжёлая работа (импорт, фиды, переиндексация) идёт только в worker, пакетами и потоково.

**Декларативный код.** Описываем *что*, а не *как*: поведение задаётся описанием (конфигом, схемой, таблицей
правил), а общий движок его исполняет. Новая сущность, правило или интеграция подключается описанием, а не
копированием императивного кода.

- Справочники с админкой — `defineCRUD` (`src/shared/crud`); новые типовые возможности (фильтр по `shop_id`, текстовые
  поля редактора, SEO-связь) добавляются в фабрику как опция, а не руками в каждый модуль.
- Входы, выходы, настройки магазина, блоки контента — zod-схемы; типы выводятся из схем (`z.infer`), формы админки
  строятся по тем же схемам.
- Реестры одной строкой на элемент: события → теги кэша (шаг 7), форматы фидов, провайдеры доставки, оплаты, SMS и
  передачи заказа, шаблоны писем, маппинг CommerceML-полей — в `src/container/common/*.ts`.
- Бизнес-правила — данные, а не ветвления: наценка, статусы товара, выбор предложения, SEO-шаблоны — таблицы
  правил с приоритетами, которые исполняет один движок; таблицы случаев — в unit-тестах.
- Сценарии — workflows из именованных шагов с откатом; роуты, подписчики и jobs — однострочные точки входа.
- Инфраструктура — желаемое состояние в Ansible (inventory + роли), а не скрипты-последовательности команд.

**Библиотеки.** Если для задачи есть надёжная библиотека — ставим её (`pnpm add` в `backend/` или `frontend/`),
а не пишем своё: TipTap для редактора, `sharp`, клиенты SFTP, генерация PDF/XLSX и т. п. Критерии: поддерживается,
типизирована, без лишних тяжёлых зависимостей. Новая зависимость упоминается в итоге сессии.

**Кэш.** Новый кэшируемый ответ (бэкенд `cached()`, витрина `cacheTag`) регистрирует свои теги в реестре
инвалидации (шаг 7). Изменение сущности → событие → сброс ключей бэкенда и ревалидация тегов витрины **своего
магазина** (сетевой сущности — всех магазинов). Без регистрации кэш не заводим.

**Тесты.** Каждый шаг пишет:

- unit-тесты на чистую логику (`*.unit.spec.ts`: расчёты, парсеры, правила, маппинги);
- интеграционные HTTP-тесты на каждый новый роут (`integration-tests/http`, `@medusajs/test-utils`): успех,
  валидация (400), доступ (401/403), «не найдено»;
- строку в `integration-tests/http/shop-isolation.spec.ts`: данные магазина A не видны по ключу и в админке
  магазина B;
- тест инвалидации, если шаг кэширует: изменение сущности → следующий запрос отдаёт свежие данные, витрине ушёл
  нужный тег;
- SEO-контракт, если шаг отдаёт индексируемые данные: canonical, robots, редирект вместо 404, JSON-LD-поля,
  отсутствие закупки и поставщика в ответе.

Для импорта — фикстуры реальных выгрузок. Внешние API (СДЭК, ЮKassa, SMS, Метрика) — через интерфейс с фейком в
тестах.

## Что уже сделано (до перехода на мультимагазин)

Всё ниже написано под один магазин. Шаги 1–6 переводят это на модель «много магазинов».

- **База РФ:** сид RUB / регион «Россия» / налоги с НДС (`src/modules/store-setup`), админка на русском, Москва.
  Файлы на диске в `backend/static`, ресайз в WebP-копии (`src/modules/file-local-resize`), файловые логи
  (`Logger.toFile`), Redis-кэш (`AbstractFetcher.cached()` — пока только по TTL), блокировки, worker отдельно от
  server. `GET /store/site-settings` пока отдаёт заглушку — хранилище появится в шаге 2.
- **Каталог и поставщики** (`supplier`, `catalog`, `attribute`, `brand`): поставщик со своим складом (stock location),
  `supplier_offer` по варианту (одна карточка — несколько поставщиков), основная категория, бренд, характеристики,
  проверка публикации (`ProductPublishGuard`). Тест — `integration-tests/http/catalog.spec.ts`.
- **URL:** slug из русского названия (`src/shared/service/slug`), CRUD-фабрика `src/shared/crud`, модуль `redirect`
  (301/302/410, без цепочек, CSV-импорт), `entity_path`, `GET /store/redirects`, фронтовый `proxy.ts`.
- **Импорт CommerceML 2** (`src/modules/exchange`): протокол 1С `/1c/exchange/:supplier` (push) и pull по HTTP,
  потоковый разбор 2.03–2.10, пачки через workflows, маппинг групп и свойств, защита ручных правок по снимку,
  `import_run` с продолжением после падения, админка «Импорт». Тест — `integration-tests/http/exchange.spec.ts`.
- **Доставка (начато):** провайдеры СДЭК и Яндекс Доставки, тариф от города склада, `GET /store/delivery/points`.
- **Контент (заготовки):** статьи (`content`, поле `body` — простой текст), посадочные (`filter-page`) — CRUD, slug,
  админка.
- **Ansible (под один магазин):** роли `common`, `docker`, `traefik`, `postgres` (с бэкапом), `redis`, `rabbitmq`,
  `backend`, `frontend`; выкат без простоя (`compose-rollout`), CI собирает образы.
- **Витрина olisa:** кэш fetch по времени (`revalidate: 60…3600`, теги `products`, `product:<handle>`), эндпоинта
  ревалидации нет.

Перенесённые хвосты: ресайз в worker и пересчёт остатков пачками — шаг 41; FTP/SFTP и ручная склейка дублей —
шаг 42; «поставщик молчит» — шаги 11 и 28; 301 для снятого товара — шаг 11; способы доставки на складах
поставщиков — шаг 30; фронтовый `images.loader` под ширины ресайза — задача фронта.

## Часть A. Фундамент сети

### Шаг 1. Модуль `shop` и создание магазина

Цель: магазин — полноценная сущность, создаётся из админки. Образец — `marketplace` (`create-vendor`).

1. Модуль `src/modules/shop`: `shop` — `slug` (уникален, `[a-z0-9-]`, служит префиксом handle), `name`, `domain`,
   `storefront_url`, `is_active`, `settings` (JSON, схема — zod в `shared`: контакты, логотип, письма, доставка,
   SEO по умолчанию — поля добавляются в своих шагах).
2. Links: `shop ↔ sales_channel` (1:1), `shop ↔ api_key` (publishable).
3. Workflow `create-shop`: sales channel → publishable key, привязанный к каналу → `shop` → корневая категория
   магазина → регион «Россия» и способы доставки доступны каналу. Откат при ошибке на любом шаге.
4. Admin API `/admin/shops` (список, создание, правка, выключение; удаления нет). Страница «Магазины» в админке:
   форма создания, показ publishable key для inventory Ansible.
5. Сид: `initial-data-seed` создаёт магазин `olisa` через тот же workflow (вместо голого sales channel).

Тесты: unit — валидация slug и схемы настроек; HTTP — CRUD `/admin/shops`, откат `create-shop` при падении шага.

### Шаг 2. Контекст магазина в запросах + сетевые настройки

Цель: любой роут знает свой магазин; у магазина есть настоящие настройки вместо заглушки.

1. Store-middleware: publishable key → sales channel → `shop` → `req.shop`. Ключ без магазина или выключенный
   магазин → 403. Хелпер `requireShop(req)` в `src/shared`. Кэш «ключ → магазин» — сразу через реестр инвалидации
   (заготовка реестра, полностью — шаг 7), сброс по `shop.updated`.
2. Admin: заголовок `x-shop-id`, хелпер `requireAdminShop(req)` (400 без заголовка для «магазинных» роутов).
   Переключатель магазина в админке (виджет в шапке плюс `localStorage`), обёртка над `fetch` в `src/admin`, которая
   подставляет заголовок.
3. Сетевые настройки — синглтон `network_settings` (в модуле `shop`): название сети, юрлицо, ИНН/ОГРН/КПП,
   юр. адрес, телефон и email сети. Форма в админке.
4. `GET /store/shop` вместо `/store/site-settings`: данные магазина и реквизиты сети (для подвала и Organization в
   schema.org). Старый роут и модуль `site-settings` удалить, фронт olisa перевести (Orval).
5. CORS: домены витрин берутся из таблицы `shop` (свой cors-middleware для `/store` и `/auth` поверх env-списка),
   чтобы новый магазин не требовал рестарта бэкенда.

Тесты: HTTP — `/store/shop` с ключами двух магазинов, без ключа, с ключом выключенного магазина; CORS-заголовки

1. Выбор предложения для продажи варианта: в наличии → минимальная закупка (или приоритет поставщика). Розница —
   от выбранного предложения.
2. Устаревшие данные: остатки поставщика не обновлялись дольше порога (настройка магазина) → его предложения
   `out_of_stock`. Флаг «поставщик молчит» на поставщике (письмо — шаг 28).
3. Статусы `in_stock` / `out_of_stock` / `preorder` / `discontinued`. `out_of_stock` — страница 200, индексируется.
   `discontinued` (давно нет ни у кого) → 301 на основную категорию или 410 (настройка магазина). Образец
   предзаказа — `preorder`.

Тесты: unit — выбор предложения и статусы; HTTP — «замолчавший» поставщик, 301 для снятого товара.

Готово, когда: поставщик, «замолчавший» на сутки, перестаёт продаваться; снятый товар даёт 301.

### Шаг 12. Срок доставки на карточке и согласованность индекса

1. Срок на карточке = сборка поставщика + транзит (оценка от города поставщика до региона по умолчанию) — для
   «доставим за N дней» и `deliveryLeadTime`.
2. Закрыть TODO из `src/search/product.ts` (события price list, batch-привязки) — индекс и кэш не должны расходиться
   с ценами после импорта.

Готово, когда: после импорта цены в поиске совпадают с ценами карточки.

### Шаг 13. SEO-метаданные

1. Модуль `seo`: `meta_title`, `meta_description`, `h1`, `seo_text`, `canonical_url`, `robots`, `og_*` + links к
   product, category, brand, collection, page, article, filter_page. Ручные правки защищены от импорта.
2. Шаблоны по умолчанию на тип сущности — в настройках магазина (`{title} купить — цена {price} ₽ | {shop}`).
3. Admin-виджеты: редактирование, превью сниппета Яндекса и Google, длины title/description.

Тесты: unit — подстановка шаблонов, обрезка по длине; HTTP — итоговые meta для каждого типа сущности.

Готово, когда: у любой индексируемой сущности есть итоговые meta по шаблону своего магазина.

### Шаг 14. Редактор контента и текстовые блоки

Цель: статьи, страницы и тексты сайта редактируются в админке визуально, без разработчика.

1. Формат контента — JSON-документ блоков (заголовки h2–h4, абзац, списки, цитата, таблица, изображение с alt и
   подписью, видео-вставка, кнопка-ссылка, «товары» — карточки по id, FAQ). Схема — zod в `src/shared`; HTML на
   сервер не принимаем. Ссылки и вставки проходят санитизацию (белый список хостов видео).
2. Редактор в админке — общий компонент `src/admin/components/content-editor` на TipTap (StarterKit + свои
   узлы под блоки), загрузка картинок через файловый модуль (ресайз из `file-local-resize` работает), выбор товаров магазина.
3. Модуль `content`: `article.body` → JSON-блоки; новая сущность `text_block` — `shop_id`, `key`
   (`home.hero`, `product.guarantee`, `footer.about`, `checkout.notice`), название, контент блоками или простой
   текст, `is_active`. Список ключей — свободный, фронт берёт нужные по ключу.
4. Store API: `GET /store/text-blocks?keys=…` (пачкой), статьи отдают блоки плюс вычисленное оглавление и время
   чтения. Изменение блока → тег `text-block:<key>` (шаг 7).
5. `seo_text` категорий и SEO-модуля (шаг 13) — тем же редактором.

Тесты: unit — zod-схема блоков, санитизация, оглавление; HTTP — CRUD текстовых блоков, изоляция по магазинам,
инвалидация тега.

Готово, когда: менеджер в админке olisa пишет статью с картинкой, таблицей и подборкой товаров и меняет текст
гарантии на карточке — изменения на витрине через секунды.

### Шаг 15. Уникализация контента и SEO-отчёт

1. Источник описания (`supplier` / `rewritten` / `manual`), очередь на переписывание с приоритетом (рекламные
   категории — выше); опционально — черновик через LLM с ручной проверкой в редакторе шага 14.
2. Отчёт по магазину: без description, дубли title, без alt, описание от поставщика, тонкие страницы (мало текста
   и товаров).
3. Межмагазинные дубли: один товар в двух магазинах сети с одинаковым описанием.

Готово, когда: отчёт показывает долю неуникальных описаний по магазину и дубли между магазинами.

### Шаг 16. Store API: страница товара

1. `GET /store/pages/product/:handle` (в рамках `req.shop`): товар, варианты, цена, наличие, срок доставки,
   изображения с alt, бренд, характеристики, крошки, SEO, текстовые блоки карточки, связанные товары. Закупка и
   поставщик наружу не отдаются.
2. Готовые поля для JSON-LD (Product, Offer, BreadcrumbList; AggregateRating — после шага 27).
3. Неизвестный handle → проверка редиректов магазина → `redirect_to` вместо 404.
4. Кэш ответа — через реестр (шаг 7). Цель по скорости — p95 < 100 мс из кэша (быстрая посадочная — дешевле клик).

Тесты: HTTP — SEO-контракт (поля JSON-LD, нет закупки, `redirect_to`), инвалидация при смене цены.

Готово, когда: страница товара olisa рендерится одним запросом; Rich Results Test проходит.

### Шаг 17. Store API: категории, бренды, коллекции, навигация

1. `GET /store/pages/category/:handle` — категория, дети, крошки, SEO, фильтры с количеством, первая страница
   товаров; сортировка, фильтры, пагинация.
2. `/store/pages/brand/:handle`, `/store/pages/collection/:handle`, `GET /store/navigation` (дерево магазина).

Готово, когда: листинг категории — один запрос, фильтры считаются по товарам магазина.

### Шаг 18. Посадочные под рекламу: SEO-фильтры и картинки категорий

1. `filter_page` на атрибутах (вместо JSON): категория + значения фильтров → свой URL, H1, SEO-текст (редактор
   шага 14), баннер. Индексируются только такие комбинации; остальные — `noindex, follow` + canonical на категорию.
2. Картинки и баннеры категорий (образец — `category-images`).
3. Параметры рекламы (`utm_*`, `yclid`, `vkclid`) не плодят дубли: canonical без них, кэш витрины их игнорирует.

Готово, когда: посадочная «категория + бренд» создаётся из админки со своими meta и баннером; URL с UTM отдаёт
тот же canonical.

### Шаг 19. Контент: страницы, статьи, сетевые юрдокументы

1. `page` в модуле `content` (блоки шага 14): `shop_id` или `null` = **сетевая** (оферта, политика ПДн, согласие).
   Магазин может переопределить сетевую страницу своей (доставка, контакты).
2. Связи статей с товарами и категориями своего магазина; FAQ (FAQPage); отложенная публикация.
3. Store-роуты страниц и статей (сетевые плюс своего магазина); SEO и редиректы из шагов 5, 13.

Готово, когда: оферта одна на сеть и видна на всех витринах; статьи магазина не видны другим.

### Шаг 20. Sitemap и robots

1. `GET /store/seo/sitemap/index` и `/store/seo/sitemap/:type?page=` — по `req.shop`: секции по 50 000 URL,
   `path`, `lastmod`, изображения; только опубликованные, индексируемые, без редиректов.
2. `GET /store/seo/robots` — Disallow из настроек магазина, «закрыть сайт» для стейджинга и неготового магазина.
3. `lastmod` меняется только при значимых изменениях.

Тесты: валидация XML по схеме sitemap; в выдаче нет `noindex` и редиректов.

Готово, когда: `sitemap.xml` olisa проходит проверку Вебмастера.

### Шаг 21. Поиск

1. Расширить индекс `product`: бренд, характеристики, наличие, основная категория, артикул и штрихкод, синонимы,
   морфология русского. Если встроенный индекс не тянет 1 млн товаров или морфологию — Meilisearch
   (образец — `meilisearch-integration`), решение — в начале сессии по замеру.
2. `GET /store/search/suggest`; логирование популярных запросов по магазину. Поиск — `noindex`.

Готово, когда: поиск находит по артикулу и словоформам, подсказки — только из своего магазина.

### Шаг 22. Товарные фиды

Детальный план первого формата (YML Яндекс Директа) — [feed-yandex.md](feed-yandex.md). Рано, потому что товарные
кампании Директа и VK работают от фида.

1. Модуль фидов с провайдерами форматов; `MedusaFeedSource` по магазину.
2. Фид принадлежит магазину: отбор (категории, бренды, только в наличии, мин. маржа), UTM, маппинг категорий;
   файл `static/feeds/<shop>/<slug>.xml`.
3. Job: после импорта поставщика пересобираются фиды его магазина, плюс по расписанию; ошибки — в отчёт.
4. Второй формат — VK (товарный фид для VK Рекламы).

Готово, когда: фиды olisa проходят проверку в кабинетах Директа и VK.

### Шаг 23. Атрибуция рекламы: метки в корзине и заказе

1. Store API принимает метки визита (`utm_*`, `yclid`, `vkclid`, client id Метрики) и пишет их в корзину; при
   оформлении — в заказ (модуль `attribution`, link к заказу).
2. Отчёт в админке: заказы и выручка по источнику и кампании, по магазину.

Готово, когда: заказ из рекламы видно в админке с кампанией.

### Шаг 24. Производительность посадочных

1. Замер p95 store-роутов шагов 16–19 (k6): < 100 мс из кэша, < 400 мс без кэша. Индексы БД с `shop_id` первым.
2. Прогрев кэша популярных и рекламных страниц после импорта и после сброса.

Готово, когда: целевые p95 выполняются на 3+ магазинах с данными.

### Шаг 25. Контракт для внешних фронтов

1. Публикация OpenAPI store-спеки (файл в репозитории плюс `GET /store/openapi.json`), changelog, правило:
   breaking change — только с новой версией роута.
2. `backend/docs/storefront.md`: как подключить новый фронт — магазин, ключ, CORS, вебхук ревалидации (шаг 7),
   какие роуты нужны для каждой страницы, обязательные SEO-правила (редиректы, sitemap, robots, canonical с UTM),
   метки атрибуции (шаг 23), текстовые блоки.
3. Контрольный набор e2e-запросов, которым внешний фронт проверяет интеграцию.

Готово, когда: по документу можно подключить новый фронт, не читая код бэкенда.

Готово, когда: одобренный отзыв меняет рейтинг на странице и в разметке.

### Шаг 28. Покупатели и 152-ФЗ

Образец входа по SMS — `phone-auth`.

1. Общий аккаунт: регистрация в любом магазине даёт вход во все (закрепить тестом). Записать магазин регистрации.
2. `GET /store/customers/me/orders` — заказы всех магазинов с полем `shop` (название, домен).
3. Модуль `consent`: тип, версия сетевого документа, дата, IP, магазин. Без согласия — нет регистрации и заказа.

5. Письма менеджеру: «поставщик молчит», сбой импорта.

Готово, когда: аккаунт из olisa входит в магазин B и видит свои заказы обоих магазинов; согласия хранятся с версией.

### Шаг 29. Избранное и повтор заказа

Образцы — `wishlist-plugin` (уже с link на sales channel), `re-order`.

2. «Повторить заказ» — только товары своего магазина, недоступные — списком.

Готово, когда: избранное в A не видно в B; повтор заказа собирает корзину.

## Часть D. Доставка, оплата, заказ

### Шаг 30. Доставка по магазинам

1. Способы доставки на складах поставщиков (наборы и зоны), вместо склада из сида.
2. Настройки магазина: включённые способы, порог бесплатной доставки. Store-фильтр способов в корзине и проверка
   при `add-shipping-method`.
3. Тариф от города поставщика; для заказа из нескольких поставщиков — сумма или максимум (настройка); самовывоз —
   только если есть пункт у поставщика; срок в ответе.

Готово, когда: корзина магазина B не видит выключенный в B способ; тариф считается от города поставщика.

### Шаг 31. Оплата: ЮKassa по магазинам

1. Провайдер `yookassa`: карты, СБП, SberPay. shopId и секрет — в настройках магазина (шифруются ключом из vault);
   провайдер выбирает их по sales channel корзины.
2. Вебхук `/hooks/yookassa/:shop` с проверкой подлинности; двухстадийная оплата — списание после подтверждения
   поставщиком (шаг 35).
3. Оплата при получении — отдельный провайдер (если поставщик поддерживает наложенный платёж).

Готово, когда: оплата СБП в двух магазинах уходит на два разных shopId.

### Шаг 32. Чеки 54-ФЗ

1. Чек через ЮKassa: позиции, НДС, предмет и способ расчёта; реквизиты юрлица — сетевые.
2. Чек возврата; повтор при сбое.

Готово, когда: оплата и возврат в тестовом режиме дают корректные чеки.

### Шаг 33. Заказ → разбиение по поставщикам

Образец — `marketplace` (`group-vendor-items`, `create-vendor-orders`, link `vendor ↔ order`).

1. Разбиение заказа по поставщикам по выбранным предложениям (шаг 11); каждой части — свой fulfillment со склада
   поставщика.
2. Повторная проверка цены и остатка при оформлении (выгрузка устарела → предупреждение покупателю или менеджеру).

Готово, когда: заказ из двух поставщиков даёт две части с правильными складами.

### Шаг 34. Передача заказа поставщику

1. Провайдеры передачи: CommerceML `orders.xml` (`type=sale&mode=query|success|file` в `/1c/exchange/:supplier`),
   email с XLSX/PDF (образец PDF — `invoice-generator`), API поставщика. Выбор — в настройках поставщика.
2. Журнал отправок, ручная переотправка.

Готово, когда: тестовый заказ уходит поставщику каждым из способов.

### Шаг 35. Обратный поток статусов

1. Подтверждение / нет в наличии / отгружено + трек → статусы заказа; списание двухстадийной оплаты после
   подтверждения.
2. «Нет в наличии» → переназначение другому поставщику магазина, иначе уведомление менеджеру.
3. Письма покупателю от магазина: создан, оплачен, подтверждён, отправлен, доставлен, отменён, «предлагаем замену»,
   просьба об отзыве. Admin: заказы по поставщикам, расхождения.

Готово, когда: корзина → СДЭК от поставщика → СБП → чек → подтверждение → трек, с письмами на каждом шаге.

## Часть E. Маркетинг сети

### Шаг 36. Промокоды, акции, скидка на первый заказ

1. Промокод сети — без условия; магазина — условие `sales_channel_id`. Создание из админки в текущем магазине
   (пресет условия) или «на всю сеть».
2. Акции — price lists магазина поверх наценки.
3. Скидка на первый заказ в сети (образец — `first-purchase-discount`).

Готово, когда: промокод магазина A не применяется в B, сетевой — применяется везде.

### Шаг 37. Бонусный счёт: начисление

Образец — `loyalty-points`.

1. Модуль `loyalty`: счёт покупателя (сетевой), журнал операций (магазин, заказ, сумма, срок сгорания).
2. Начисление после доставки заказа (процент — сетевая настройка, магазин может переопределить); списание назад
   при возврате.
3. `GET /store/customers/me/loyalty` — баланс и история.

Готово, когда: доставленный заказ в A начисляет баллы, видимые в B.

### Шаг 38. Бонусный счёт: списание

1. Оплата баллами в корзине любого магазина (лимит — % от суммы) через promotion, как в образце, с правильным
   отражением в чеке 54-ФЗ.
2. Возврат баллов при отмене; защита от двойного списания (блокировка на счёт).

Готово, когда: баллы, начисленные в A, списываются в B, чек корректный, отмена возвращает баллы.

### Шаг 39. Офлайн-конверсии для рекламы

Образец серверной отправки событий — `segment-integration`.

1. Отправка заказов и смен статуса (оплачен, доставлен, отменён) в Яндекс Метрику (офлайн-конверсии по client id /
   `yclid`) и VK Рекламу — по меткам шага 23, счётчики и токены — в настройках магазина.
2. Очередь отправок с ретраями, журнал в админке.

Готово, когда: оплаченный заказ из Директа виден в Метрике как конверсия своей кампании.

### Шаг 40. Возврат покупателей: брошенные корзины и «сообщить о поступлении»

Образцы — `abandoned-cart`, `restock-notification`.

1. Job брошенных корзин (с согласием на рассылку) → письмо от магазина.
2. Подписка на поступление варианта → письмо, когда поставщик вернул остаток.

Готово, когда: оба письма приходят в Mailpit в нужный момент.

## Часть F. Масштаб, эксплуатация, запуск

### Шаг 41. Импорт под нагрузку сети

1. Очередь импортов: глобальный лимит параллельных импортов и лимит на магазин, приоритет инкрементальных выгрузок
   (цены и остатки) над полными. Несколько worker-ов (число — переменная Ansible).
2. Пересчёт остатков поставщика пачками; ресайз картинок импорта — в worker, не в запросе.

Готово, когда: 50 поставщиков одновременно не блокируют друг друга и store API.

### Шаг 42. Импорт: FTP/SFTP и ручная склейка дублей

1. `DownloadTransport` для FTP/SFTP.
2. Ручная склейка и расклейка дублей в админке (внутри магазина).

Готово, когда: поставщик с FTP загружается по расписанию; два дубля склеиваются из админки.

### Шаг 43. Доступы менеджеров по магазинам

Образец — `marketplace` (`vendor-admin`).

1. Link `user ↔ shop`; admin-middleware: `x-shop-id` должен быть в списке пользователя, у суперадмина — все.
2. Ограничение ключевых core-роутов (товары, заказы) через middleware-фильтр по sales channel. Что ограничить нельзя —
   задокументировать.

Готово, когда: менеджер магазина A не может прочитать поставщиков и заказы B.

### Шаг 44. Безопасность, наблюдаемость, бэкапы, CI

1. Rate limit на auth, отзывы, поиск (по магазину и IP); `/1c/exchange` — Basic-auth плюс опциональный
   IP-allowlist; лимит размера загрузки.
2. Health server и worker; метрики с меткой магазина: импорт, возраст данных поставщика, очереди, вебхуки,
   ревалидации, отправки заказов. Ошибки — в Sentry/GlitchTip с тегом `shop` (образец — `sentry-integration`);
   сервис мониторинга разворачивается ролью Ansible.
3. Бэкапы Postgres и `backend/static` по расписанию с выгрузкой во внешнее хранилище, ежемесячная проверка
   восстановления playbook'ом, ротация логов, архив CommerceML-пакетов.
4. CI: lint, типы, тесты (включая изоляцию и инвалидацию), актуальность OAS, `ansible-lint`.

Готово, когда: нагрузочный тест проходит во время импорта; сбой импорта или передачи заказа виден в алерте с
указанием магазина; восстановление из бэкапа проверено командой.

### Шаг 45. Запуск olisa

1. Поставщики подключены, маппинг заполнен, очередь «требует разбора» пуста.
2. Наценки проверены на выборке; нет товаров с ценой ниже закупки.
3. SEO-отчёт без критичных пробелов; приоритетные и рекламные описания переписаны.
4. Редиректы со старого сайта загружены; sitemap и robots отдаются; стейджинг закрыт.
5. Фиды подключены в Директе и VK; офлайн-конверсии приходят.
6. Тестовые заказы через каждого поставщика, способ доставки и оплаты, возврат с чеком.
7. Вебмастер и Search Console подтверждены. После релиза — только новые миграции.

### Шаг 46. Второй магазин сети

1. Магазин создан в админке, фронт из своего репозитория выкачен по чеклисту шага 9.
2. Прогон `shop-isolation.spec.ts` и контрольного набора шага 25 на проде.

Готово, когда: два магазина работают на одном бэкенде, общий покупатель видит заказы обоих.
