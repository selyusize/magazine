# План бэкенда (Medusa 2) — SEO-ориентированный дропшиппинг-магазин

Линейный план: этапы идут строго по порядку, каждый опирается на предыдущие.
Этап закрыт, когда выполнены все пункты «Готово, когда».

Контекст: Medusa 2.21, рынок РФ (RUB, НДС, ЮKassa/СБП, СДЭК, 54-ФЗ, 152-ФЗ),
self-hosted Docker, фронт — Next 16 (рендер страниц и sitemap на его стороне,
бэкенд отдаёт данные). Шаблон переиспользуется для разных магазинов — всё
магазинно-специфичное выносится в конфиг/env/админку, не в код.

Модель бизнеса — **дропшиппинг**: своего склада нет. Каталог, цены закупки и остатки
приходят от поставщиков в формате **CommerceML 2** (выгрузка 1С/МойСклад/УТ), заказы
передаются поставщику, он же отгружает. Поставщиков может быть несколько.

Сквозные правила для всех этапов:

- Новый кастомный роут — с блоком `@oas`, затем `pnpm openapi:generate` → Orval на фронте.
- Бизнес-логика — в workflows/модулях; роуты тонкие (`Action` → `CommandHandler`/`Fetcher`
из `src/shared/contract`), зависимости — через `src/container`.
- Тяжёлая работа (импорт, фиды, переиндексация) — только в worker, пакетами, потоково.
- Любое изменение SEO-значимых данных порождает событие → ревалидация фронта (этап 9).
- Каждый этап покрыт интеграционными тестами (`@medusajs/test-utils`); для импорта —
фикстуры реальных CommerceML-выгрузок.

## Этап 4. Импорт CommerceML 2 (ключевой этап)

Цель: каталог, цены и остатки поставщиков попадают в магазин автоматически, полностью
и инкрементально, без ручной работы.

### 4.1. Получение файлов — два режима на поставщика

1. **Push (стандартный протокол обмена 1С с сайтом)** — роут `/1c/exchange/:supplier`:
  - `type=catalog&mode=checkauth` — Basic-auth по логину/паролю поставщика, ответ
   `success\n<cookie_name>\n<cookie_value>`;
  - `mode=init` — `zip=yes\nfile_limit=<байт>`;
  - `mode=file&filename=` — приём файла (в т. ч. zip частями, дозапись), сохранение в `backend/exchange/<поставщик>/<запуск>`;
  - `mode=import&filename=` — ставит импорт в очередь, отвечает `progress` пока идёт,
  затем `success` / `failure\n<причина>`;
  - `type=sale&mode=query|success|file` — обмен заказами (этап 15).
2. **Pull** — scheduled job скачивает выгрузку по расписанию: URL (HTTP с auth), FTP/SFTP,
  zip-архив. Большинство дропшип-поставщиков отдают именно ссылку на XML.
3. Оба режима складывают пакет (`import.xml`, `offers.xml`, картинки) в `backend/exchange` и создают
  запись `import_run` — дальше обработка общая.



### 4.2. Разбор

1. Потоковый SAX-парсер (файлы на сотни МБ не грузятся в память целиком), кодировки
  UTF-8 и windows-1251, версии схемы 2.03–2.10.
2. `import.xml`:
  - `Классификатор/Группы` → дерево групп поставщика (хранится как справочник);
  - `Классификатор/Свойства` + справочники значений → атрибуты поставщика;
  - `Каталог/Товары/Товар`: `Ид`, `Артикул`, `Штрихкод`, `Наименование`, `Описание`,
  `Группы`, `Картинка`, `ЗначенияСвойств`, `ЗначенияРеквизитов`, `Изготовитель`/бренд;
  - `СодержитТолькоИзменения` → инкрементальный режим (не снимать отсутствующее).
3. `offers.xml`: `ТипыЦен` (выбор нужного типа цены в настройках поставщика),
  `Предложения`: `Ид` вида `товар#характеристика` → варианты, `ХарактеристикиТовара`
   → опции варианта, `Цены`, `Количество`/`Остатки`.
4. Отдельные `prices.xml`/`rests.xml` (разбитые выгрузки) — поддержать как частный
  случай offers.



### 4.3. Сопоставление (маппинг)

1. Группы поставщика → категории магазина: таблица маппинга в админке. Немаппленные
  группы — товары импортируются в статусе `draft` и попадают в очередь «требует разбора».
2. Свойства поставщика → атрибуты магазина (и их значения): маппинг + авто-создание
  по совпадению названия. Неизвестные — сохраняются в metadata, не теряются.
3. Бренд — из свойства/реквизита, нормализация написания (справочник синонимов).
4. **Склейка дублей между поставщиками**: поиск существующего товара по штрихкоду →
  артикулу производителя + бренду → (опционально) вручную в админке. Совпал — к карточке
   добавляется ещё одно `supplier_offer`, новая карточка не создаётся.



### 4.4. Запись

1. Импорт — workflow в worker, пакетами по N товаров, идемпотентный (upsert по
  `supplier_id + Ид`), с возможностью продолжить с места падения.
2. Новый товар: `handle` (этап 3), статус `draft` или `published` по настройке поставщика
  и прохождению обязательных полей.
3. Изображения: скачиваются к себе и проходят ресайз (этап 1.5) — без хотлинка на поставщика;
  дедуп по хэшу, повторно не качаются и не пережимаются, alt генерируется из названия.
4. **Защита ручных правок**: поля, изменённые в админке (название, описание, handle,
  категория, SEO, фото), помечаются как «управляется вручную» и импортом не
   перезаписываются. Цены и остатки обновляются всегда.
5. Полная выгрузка: товары поставщика, которых нет в файле, — остаток 0 у этого
  предложения (не удаление карточки).
6. События пачкой по завершении (не по одному на товар) — для поиска, кэша, sitemap.



### 4.5. Контроль

1. `import_run`: поставщик, файлы, режим, статус, счётчики (создано / обновлено /
  пропущено / ошибок), длительность, лог ошибок по товарам; подробный лог запуска —
   `Logger.toFile("import-<поставщик>")` → `backend/logs/import-<поставщик>.log`.
2. Admin: страница поставщиков, история импортов, ручной запуск, очередь «требует
  разбора» (немаппленные группы, подозрения на дубли, товары без фото/цены).
3. Алерт, если поставщик не обновлялся дольше N часов (см. этап 5.4).

Готово, когда: реальная выгрузка поставщика (полная и инкрементальная, push и pull)
загружается без ручных правок; повторный импорт того же файла ничего не меняет;
товар двух поставщиков — одна карточка.

## Этап 5. Цены, наличие и жизненный цикл товара

Цель: розничная цена и наличие всегда актуальны и честны — для покупателя и сниппетов.

1. **Наценка**: правила по поставщику → категории → бренду → товару (приоритет у
  частного), процент и/или фикс, минимальная маржа в рублях, округление (до 10 ₽,
   «…990»). Розничная цена пересчитывается при каждом изменении закупки и правил.
2. Рекомендованная розничная цена поставщика (если есть в типах цен) — как «старая цена»
  или как потолок, настраивается.
3. **Выбор предложения** для продажи варианта: в наличии → минимальная закупка
  (или приоритет поставщика). Розничная цена — от выбранного предложения.
4. **Устаревшие данные**: если остатки поставщика не обновлялись дольше порога —
  его предложения считаются `out_of_stock` (не продаём то, чего, возможно, нет).
5. Статус товара: `in_stock` / `out_of_stock` / `preorder` / `discontinued`.
  `out_of_stock` — страница 200 и индексируемая (теряем позиции, если 404);
   `discontinued` (давно нет ни у кого) — 301 по этапу 3.
6. Срок доставки на карточке = срок сборки поставщика + транзит (для «доставим за N дней»
  и `deliveryLeadTime` в разметке).
7. Акции — price lists поверх наценки.
8. Закрыть TODO из `src/search/product.ts` (события на price list, batch-привязки),
  иначе индекс и кэш расходятся с ценами после импорта.

Готово, когда: изменение закупки в выгрузке меняет розничную цену по правилам;
поставщик, «замолчавший» на сутки, перестаёт продаваться.

## Этап 6. Модуль SEO-метаданных и уникализация контента

Цель: полный контроль мета-данных; борьба с неуникальными описаниями поставщика.

1. Модуль `seo`: `meta_title`, `meta_description`, `h1`, `seo_text`, `canonical_url`,
  `robots`, `og_*` + links к product, category, brand, collection, page, article,
   filter_page. Изменённое вручную — защищено от импорта (этап 4.4).
2. Шаблоны по умолчанию на тип сущности (`{title} купить — цена {price} ₽ | {site}`).
3. **Уникальность контента** (у дропшипа описания одинаковы у сотен сайтов):
  флаг источника описания (`supplier` / `rewritten` / `manual`), очередь на переписывание
   с приоритетом по трафику/категории; опционально генерация черновика через LLM с
   ручной проверкой. Таблица характеристик и уникальные блоки (доставка, гарантия,
   отзывы) уже добавляют уникальность.
4. Admin-виджеты: редактирование SEO, превью сниппета, длины title/description.
5. Отчёт: без description, дубли title, без alt, описание от поставщика.

Готово, когда: у любой индексируемой сущности есть итоговые meta; отчёт показывает
долю неуникальных описаний.

## Этап 7. Store API для страниц

Цель: один запрос на страницу, все данные для SSR и schema.org.

1. `GET /store/pages/product/:handle` — товар, варианты, цена, наличие, срок доставки,
  изображения с alt, бренд, характеристики, крошки, SEO, рейтинг (этап 12), связанные
   товары. Закупка и поставщик наружу **не отдаются**.
2. `GET /store/pages/category/:handle` — категория, дети, крошки, SEO, фильтры с
  количеством, первая страница товаров; сортировка/фильтры/пагинация.
3. `/store/pages/brand/:handle`, `/store/pages/collection/:handle`, `GET /store/navigation`.
4. Готовые поля для JSON-LD (Product, Offer, AggregateRating, BreadcrumbList).
5. Неизвестный handle → проверка редиректов → `redirect_to` вместо 404.

Готово, когда: страницы рендерятся одним запросом; Rich Results Test проходит.

## Этап 8. Поиск и SEO-фильтры

1. Расширить индекс `product`: бренд, характеристики, наличие, основная категория,
  артикул/штрихкод; синонимы, морфология русского.
2. Модуль `filter_page` (заготовка есть: CRUD, slug, `/catalog/{категория}/{handle}`, админка; фильтры — JSON
  до появления атрибутов): категория + значения фильтров → свой URL и SEO. Только такие
   комбинации индексируемы, остальные — `noindex, follow` + canonical на категорию.
3. Поиск — `noindex`; логирование популярных запросов; `GET /store/search/suggest`.

Готово, когда: посадочная «категория + бренд» создаётся из админки со своими meta.

## Этап 9. Кэширование и ревалидация фронта

1. Кэш store-роутов этапа 7 в Redis с инвалидацией по событиям.
2. Диспетчер: событие → теги (`product:<handle>`, `category:<handle>`, `navigation`,
  `sitemap`) → POST на фронт `/api/revalidate` с секретом; дебаунс и ретраи через workflow.
   После импорта — одна пачка ревалидаций, а не тысячи запросов.
3. `Cache-Control`/`ETag` на GET store API.

Готово, когда: обновление остатков из выгрузки видно на сайте за минуты без перезапуска.

## Этап 10. Данные для sitemap и robots

1. `GET /store/seo/sitemap/index` — секции и число страниц по 50 000 URL.
2. `GET /store/seo/sitemap/:type?page=` — `path`, `lastmod`, изображения; только
  опубликованные, индексируемые, без редиректов.
3. `GET /store/seo/robots` — доп. Disallow из админки, «закрыть сайт» для стейджинга.
4. `lastmod` меняется только при значимых изменениях (не при каждом импорте остатков).

Готово, когда: `sitemap.xml` фронта проходит проверку Вебмастера/Search Console.

## Этап 11. Контент: страницы и блог

1. Модуль `content`: `page` (доставка, оплата, возврат, оферта, ПДн, контакты) и `article` (статьи уже есть:
  CRUD, slug, `/blog/{handle}`, админка, статус черновик/опубликована).
2. Связи статей с товарами и категориями; FAQ-блоки (FAQPage).
3. Store-роуты страниц и статей; SEO и редиректы из этапов 3, 6; отложенная публикация.

Готово, когда: статьи создаются в админке и попадают в sitemap.

## Этап 12. Отзывы и вопросы

1. Модуль `review`: оценка, текст, плюсы/минусы, фото, «подтверждённая покупка»,
  модерация, ответ магазина; вопросы — тот же модуль.
2. Агрегат рейтинга на товаре → AggregateRating. Отзывы привязаны к карточке, а не к
  поставщику — сохраняются при смене поставщика.
3. Антиспам: rate limit, капча.

Готово, когда: одобренный отзыв меняет рейтинг на странице и в разметке.

## Этап 13. Товарные фиды

Детальный план первого формата (YML Яндекс Директа) — [feed-yandex.md](feed-yandex.md).

1. Модуль фидов с провайдерами форматов: YML (Яндекс), Google Merchant, VK.
2. Настройка в админке: отбор (категории, бренды, только в наличии, мин. маржа),
  UTM, маппинг категорий.
3. Job собирает потоково в `backend/static/feeds/<slug>.xml` после каждого импорта и по расписанию.
4. Товары с ошибками — в отчёт, не в фид.

Готово, когда: фиды проходят проверку в кабинетах площадок.

## Этап 14. Покупатели и 152-ФЗ

1. Email+пароль (есть), вход по SMS-коду (провайдер через интерфейс).
2. Модуль `consent`: тип, версия документа, дата, IP. Без согласия — нет регистрации/заказа.
3. Обезличивание по запросу; передача ПДн поставщику для отгрузки — отдельным пунктом
  в согласии и в политике.

Готово, когда: согласия хранятся с версией; удаление обезличивает покупателя.

## Этап 15. Заказы → поставщику

Цель: заказ покупателя автоматически превращается в заказы поставщикам.

1. **Разделение заказа** по поставщикам по выбранным предложениям (этап 5.3);
  каждой части — свой fulfillment (stock location поставщика).
2. Повторная проверка цены и остатка в момент оформления (если выгрузка устарела —
  предупреждение покупателю/менеджеру).
3. Передача поставщику через провайдеры: CommerceML `orders.xml` (выдача по
  `type=sale&mode=query`, подтверждение `mode=success`, приём статусов `mode=file`),
   email с XLSX/PDF, API поставщика. Выбор — в настройке поставщика.
4. Обратный поток: подтверждение / нет в наличии / отгружено + трек-номер → статусы
  заказа и письма покупателю. «Нет в наличии» → попытка переназначить другому
   поставщику, иначе — уведомление менеджеру.
5. Admin: заказы по поставщикам, расхождения, ручная переотправка.

Готово, когда: тестовый заказ из двух поставщиков уходит обоим, статусы и трек
возвращаются в заказ.

## Этап 16. Доставка и оплата

> Начат раньше (2026-10-03): провайдеры **СДЭК** и **Яндекс Доставки** — тариф в корзине от города склада отгрузки
> (до ПВЗ и курьером), `GET /store/delivery/points` с кэшем; сид создаёт склад-заглушку «Отгрузка» (Москва), зону
> «Россия» и способы доставки. Осталось: Почта России и Ozon Доставка (по решению — позже); создание отправлений,
> трек, этикетки — с этапом 15; самовывоз — с пунктов поставщиков, после этапа 2; срок доставки в ответе
> (провайдеры его уже получают от перевозчиков); фронт — выбор способа и карта ПВЗ.

1. Доставку отгружает поставщик: расчёт тарифа СДЭК/Почты **от города поставщика**,
  срок = сборка + транзит. Для разделённого заказа — сумма/максимум по частям
   (правило в настройке). Самовывоз — только если есть пункт у поставщика.
2. `GET /store/delivery/points?city=` — ПВЗ для карты.
3. ЮKassa: карты, СБП, SberPay, вебхуки с проверкой; рекомендуется двухстадийная
  оплата — списание после подтверждения поставщиком.
4. Чеки 54-ФЗ (позиции, НДС, предмет/способ расчёта), чек возврата.
5. Оплата при получении — отдельный провайдер (если поставщик поддерживает наложенный платёж).

Готово, когда: корзина → СДЭК от поставщика → оплата СБП → чек → подтверждение
поставщиком → трек.

## Этап 17. Уведомления

1. Notification-провайдер поверх `SMTP` (`src/shared/service/smtp`).
2. Шаблоны на русском: регистрация, сброс пароля, заказ создан/оплачен/подтверждён/

3. Менеджеру: новый заказ, отказ поставщика, сбой импорта, «замолчавший» поставщик

Готово, когда: весь путь заказа и сбои импорта сопровождаются письмами (Mailpit).

## Этап 18. Производительность и безопасность

1. Индексы БД под этапы 4, 7–10; импорт 100k+ предложений укладывается в целевое время,
  не блокируя store API (worker отдельно от server — уже есть `MEDUSA_WORKER_MODE`).
2. p95 store-роутов страниц < 100 мс из кэша, < 400 мс без кэша (k6).
3. Rate limit на auth, отзывы, поиск; `/1c/exchange` — только Basic-auth +
  опционально IP-allowlist поставщика; лимит размера загрузки.
4. Изображения: ресайз уже на бэкенде (этап 1.5); перед бэкендом — nginx/CDN, отдающий
  `static/` напрямую с диска, минуя Node.

Готово, когда: нагрузочный тест проходит во время работающего импорта.

## Этап 19. Наблюдаемость, тесты, бэкапы

1. Логи, health server/worker, метрики: длительность и ошибки импорта по поставщикам,
  возраст данных поставщика, очереди, вебхуки.
2. Ошибки — в Sentry/GlitchTip.
3. Ежедневные бэкапы Postgres и `backend/static` (оригиналы; размеры можно перегенерировать),
  проверка восстановления; ротация `backend/logs` (logrotate); архив исходных
   CommerceML-пакетов за N дней (для разбора споров о ценах).
4. CI: lint, типы, тесты, актуальность OAS-клиента фронта.

Готово, когда: сбой импорта или передачи заказа виден в алерте.

## Этап 20. Запуск

1. Поставщики подключены, маппинг групп и свойств заполнен, очередь «требует разбора» пуста.
2. Наценки проверены на выборке; нет товаров с ценой ниже закупки.
3. Отчёт SEO-пробелов без критичных; приоритетные описания переписаны.
4. Редиректы со старого сайта загружены; sitemap/robots отдаются; стейджинг закрыт.
5. Фиды подключены в кабинетах.
6. Тестовые заказы через каждого поставщика, каждый способ доставки и оплаты, возврат с чеком.
7. Вебмастер и Search Console подтверждены, sitemap отправлен.
