# Контракт витрины магазина

Что должен уметь фронт любого магазина сети Snowaa (olisa — `frontend/` в этом репозитории, остальные — в своих
репозиториях), чтобы работать с бэкендом. Дополняется в шаге 25 плана (полная спецификация Store API и SDK).

## Вебхук ревалидации кэша

Изменение в админке (товар, категория, бренд, редирект, реквизиты…) через секунды сбрасывает кэш витрины **своего
магазина**: бэкенд копит теги за окно дебаунса и шлёт их одной пачкой. TTL кэша на витрине — только страховка на
случай, если вебхук не дошёл.

### Запрос

```http
POST {storefront_url}/api/revalidate
Content-Type: application/json
x-revalidate-secret: <секрет магазина>

{ "tags": ["brand:philips", "brands", "products", "sitemap"] }
```

- `storefront_url` — поле магазина в админке («Магазины»); путь `/api/revalidate` фиксирован.
- Секрет — у каждого магазина свой: админка → «Обновление витрины» (там же перевыпуск). На витрине — env
  `REVALIDATE_SECRET`, на сервере — vault Ansible (`vault_storefront_revalidate_secret`). Сравнивать за
  постоянное время.
- Теги приходят без магазина и без префикса handle: один фронт — один магазин.

### Ответ

| Код | Когда | Что делает бэкенд |
| --- | --- | --- |
| 2xx | теги сброшены | пачка `sent` |
| 401 | неверный или пустой секрет | повтор через 10 с, 1 мин, 5 мин, 15 мин, 1 ч, затем `failed` |
| 400 | тело не `{ tags: string[] }` | повторы, как выше |
| нет ответа за 10 с | витрина недоступна | повторы, как выше |

Журнал отправок (теги, статус, неудачи, ответ, время следующей попытки) — админка → «Обновление витрины». Там же
кнопка «Обновить витрину целиком» — все групповые теги разом (`POST /admin/storefront-revalidations`).

### Теги

Групповой тег ставится на **каждый** запрос своей группы, тег сущности — ещё и на запросы этой сущности (handle из
URL витрины). Словарь — `src/shared/service/cache-invalidation/storefront-tags.ts`, у olisa —
`frontend/src/shared/api/cache-tags.ts`.

| Тег | На каких запросах | Когда приходит |
| --- | --- | --- |
| `shop` | `/store/shop`: подвал, контакты, Organization | магазин изменён, реквизиты сети изменены (всем магазинам) |
| `products` | все запросы товаров: листинги, поиск, карточки | товар, вариант (цена, остаток), бренд, характеристика, регион, конец импорта |
| `product:<handle>` | карточка товара | товар или его вариант изменён, создан, удалён |
| `categories`, `category:<handle>` | категории, страница категории | категория изменена; `category:<handle>` — ещё посадочная этой категории |
| `navigation` | меню, дерево категорий | категория изменена, конец импорта |
| `collections`, `collection:<handle>` | коллекции | коллекция изменена |
| `brands`, `brand:<handle>` | бренды | бренд изменён, конец импорта |
| `articles`, `article:<handle>` | статьи | статья изменена |
| `filter-pages`, `filter-page:<категория>/<handle>` | посадочные | посадочная изменена |
| `redirects` | таблица редиректов (`GET /store/redirects`) | правило добавлено, удалено, импортировано, 301/410 при смене адреса |
| `sitemap` | sitemap | любая индексируемая сущность изменена |
| `regions` | регионы, валюта цен | регион изменён (всем магазинам) |

- Больше 100 тегов сущностей в пачке (импорт) — они заменяются групповыми: придёт `products` вместо тысяч
  `product:<handle>`. Поэтому групповой тег обязателен на каждом запросе группы.
- Неизвестный тег витрина просто сбрасывает (`revalidateTag` ничего не найдёт) — новые теги не ломают старые фронты.
- Удалённая сущность, магазин которой уже не определить, — групповые теги уходят всем магазинам.

### Реализация у olisa

- `app/api/revalidate/route.ts` → `src/shared/revalidate`: проверка секрета, zod-схема тела,
  `revalidateTag(tag, { expire: 0 })` — следующий запрос идёт в Medusa, а не отдаёт старое.
- Тег `redirects` ещё и перечитывает таблицу редиректов `proxy.ts` (`invalidateRedirectRules`): таблица живёт в
  памяти процесса (`globalThis` — proxy и роут собираются в разные бандлы).
- Теги на fetch — `cacheTags` из `@shared/api` в `entities/*/api`.

### Как это устроено на бэкенде

Событие изменения → реестр `src/container/common/cache.ts` (событие → теги кэша бэкенда и теги витрины + где у
сущности магазин) → подписчик `cache-invalidation` → `invalidate-caches-by-event`: сброс кэша бэкенда сразу, теги
витрины — в пачку магазина (`storefront_revalidation`, `queue-storefront-revalidations`). Новая пачка ставит
событие `storefront_revalidation.queued` с задержкой на окно (`STOREFRONT_REVALIDATE_WINDOW_MS`, 3 с); каждое
новое событие сдвигает срок, но не дальше `STOREFRONT_REVALIDATE_MAX_WAIT_MS` (30 с) от первого — импорт шлёт пачку
раз в 30 с, а не на каждый товар. `send-storefront-revalidation` захватывает пачку под блокировкой магазина, шлёт
вебхук, пишет итог и при неудаче ставит повтор. Потерянные таймеры подбирает job
`shop-requeue-storefront-revalidations` (раз в минуту), журнал старше 7 дней чистит
`shop-prune-storefront-revalidations`.

Секрет хранится зашифрованным (`SecretBox`, AES-256-GCM, ключ `SHOP_SECRETS_KEY`). Переменные бэкенда:

| Переменная | Зачем |
| --- | --- |
| `SHOP_SECRETS_KEY` | ключ шифрования секретов магазинов; на проде обязателен, в dev — от `COOKIE_SECRET` |
| `INITIAL_SHOP_REVALIDATE_SECRET` | секрет магазина из сида (olisa); `make dev-key` кладёт его во фронт |
| `STOREFRONT_REVALIDATE_WINDOW_MS`, `STOREFRONT_REVALIDATE_MAX_WAIT_MS` | окно дебаунса и потолок ожидания |
| `STOREFRONT_REVALIDATE_TIMEOUT_MS` | сколько ждать ответа витрины (10 с) |
| `STOREFRONT_REVALIDATE_HOSTS` | кому можно слать (через запятую); пусто — всем. Тесты — только `127.0.0.1` |
