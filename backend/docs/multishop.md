# Мультимагазин: как бэкенд делит сеть на магазины

Один бэкенд Medusa обслуживает сеть магазинов Snowaa: у каждого свой фронт, домен, каталог, справочники, контент и
адреса. Общие на сеть — покупатели, заказы, доставка, оплата, юрлицо. Этот документ — карта правил; подробности
реализации — `arch-guide.md` (п.3 «CRUD», п.9 «Магазин запроса и доступ к сущностям магазина»).

## Магазин

Модуль `shop` (`src/modules/shop`): `slug` (`[a-z0-9-]`, не меняется — префикс handle), `name`, `domain`,
`storefront_url`, `is_active`, `root_category_id`, `settings` (zod-схема `src/shared/shop/shop-settings.ts`).
Связи: `shop ↔ sales_channel` (1:1), `shop ↔ api_key` (publishable), `shop ↔ product_category` (дерево),
`shop ↔ product_collection`.

Создаётся кнопкой в админке (`POST /admin/shops` → workflow `create-shop`): канал продаж → publishable-ключ →
корневая категория `{slug}ːcatalog` → магазин и связи → склады с доставкой открыты каналу. Сид создаёт `olisa` тем же
workflow. Удаления нет — только выключение (`is_active: false`).

## Как запрос узнаёт магазин

Общие middleware — `src/api/middlewares/shop-context.ts`, подключены первыми:

| API | Откуда магазин | Нет магазина |
| --- | --- | --- |
| Store (`/store/*`) | publishable-ключ → канал → магазин (`req.shop`) | ключ без магазина или выключенный магазин — 403 |
| Admin (`/admin/*`) | заголовок `x-shop-id` (переключатель магазина в админке, `adminFetch`) | «магазинный» роут — 400 |

Actions берут магазин через `requireShop(req)` (Store) и `requireAdminShop(req)` (Admin) и передают `shop_id` в
Command / Query. Handler и Fetcher про HTTP не знают: их же вызывают импорт и jobs, которые работают на всю сеть.

CORS: домены витрин берутся из таблицы `shop` — новый магазин не требует рестарта.

## Чьё это: сущность магазина или сетевая

| Сущность | Где магазин | Как изолирована |
| --- | --- | --- |
| Товар | его единственный канал продаж (`sales_channels.shop`) | хуки товара: 0 или 2+ магазина — 400; Store — каналом ключа (Medusa) |
| Категория | связь `shop ↔ product_category` | хук создания — магазин родителя; Store — `storeShopScopedRoutes` |
| Коллекция | связь `shop ↔ product_collection` (не меняется) | хук создания (`additional_data.shop_id` или префикс handle) либо выбор в карточке; товары — только её магазина; Store — `storeShopScopedRoutes` |
| Поставщик, бренд, характеристика, статья, посадочная, редирект | поле `shop_id` | CRUD `shopScoped`, по id — `shopOwnedRoutes` |
| Склад, предложение, запуск импорта, группа и свойство поставщика | через поставщика (`supplier.shop_id`) | `shopScoped: { through }`, `shopOwnedRoutes` |
| Путь сущности (`entity_path`) | поле `shop_id` | пишет только модуль redirect |
| Корзина | её канал продаж | Store — `storeShopOwnedRoutes` (чужая по id — 404) |
| Покупатель, заказ, регион, доставка, оплата, налоги, теги и типы товаров | **сеть** | «Мои заказы» — все магазины |
| Реквизиты сети (`network_settings`), магазины (`/admin/shops`) | **сеть** | только админка |
| Пачка ревалидации витрины (`storefront_revalidation`), секрет вебхука | поле `shop_id` / у магазина | только текущий магазин админки (`/admin/storefront-revalidations`, `/admin/shops/current/revalidate-secret`) |

Правила для новой сущности:

1. Сущность магазина — поле `shop_id` (после создания не меняется), индексы начинаются с `shop_id`, уникальность
   handle — `(shop_id, …)`. Сетевая — явно помечена в JSDoc сущности.
2. Справочник с админкой — `defineCRUD({ shopScoped: true, handle: { scope: ["shop_id"] } })`; ссылка в теле на
   сущность магазина — `shopReferences` (400 на чужую).
3. Роуты по id — строка в `shopOwnedRoutes` (`src/container/common/shop.ts`): чужая и несуществующая — одинаково 404.
4. Ссылка на сущность другого магазина в команде — `INVALID_DATA` (`foreignShopError`).
5. Строка в `integration-tests/http/shop-isolation.spec.ts`: данные магазина A не видны и не меняются из B.
6. Сущность, которую показывает витрина, — строка в реестре инвалидации `src/container/common/cache.ts`: где у неё
   магазин и какие теги витрины сбрасывает её изменение (контракт — `docs/storefront.md`).

## Кэш и ревалидация витрин

Изменение сущности → её кэш удалён везде за секунды: кэш бэкенда (`cached(..., tags)`) — сразу, кэш витрины —
вебхуком `POST {storefront_url}/api/revalidate` только **её магазину** (сетевой сущности — всем активным
магазинам). Пачка тегов на магазин копится в окне дебаунса, отправки и повторы видны в админке («Обновление
витрины»). Контракт для фронтов и устройство — `docs/storefront.md`.

## Handle и адреса

- **Handle сущностей Medusa** (товар, категория, коллекция) уникален в Medusa на всю сеть, поэтому в БД он
  `{slug}ː{handle}` — `olisaːutyug-philips` (разделитель U+02D0: `--` модуль товаров Medusa не пропускает).
  Наружу — всегда без префикса: ответы Store API проходят через `PublishStoreHandlesMiddleware`, фильтры `?handle=`
  роутов Medusa переводит реестр `storeHandleParams`. Все преобразования — `src/shared/shop/shop-handle.ts`.
- **Handle своих сущностей** (бренд, статья, посадочная) — без префикса, уникален в магазине (`(shop_id, handle)`).
- **Синхронизация адреса** (`redirect/command/sync-entity-url`): handle из админки Medusa (кириллица, без префикса)
  приводится к `{slug}ː{slug-из-названия}`; смена handle — 301 со старого пути, удаление — 410. Пути и редиректы —
  в магазине сущности (`URL_ENTITIES[type].shopOf`). Одинаковый путь в двух магазинах — две разные страницы.
- **Импорт** пишет handle новой карточки сразу с префиксом магазина поставщика; склейка дублей — только внутри
  магазина.

## Store API: что видит витрина

| Роут | Изоляция |
| --- | --- |
| `/store/products`, `/store/products/:id` | Medusa — канал publishable-ключа |
| `POST /store/search` | Medusa — `sales_channel_ids` ключа в индексе `product` |
| `/store/product-categories`, `/store/collections` (+ `/:id`) | `storeShopScopedRoutes`: список — префикс handle магазина, чужая по id — 404 |
| `/store/carts/:id/*` | `storeShopOwnedRoutes`: корзина другого магазина — 404 |
| `/store/redirects`, `/store/redirects/resolve` | только правила `req.shop` |
| `/store/shop` | магазин ключа + реквизиты сети |

## Admin API и админка

- Свои разделы (поставщики, импорт, бренды, характеристики, статьи, посадочные, редиректы, блоки карточки товара)
  работают в текущем магазине переключателя (`x-shop-id`); блоки карточки товара — в магазине товара.
- Разделы Medusa (товары, категории, коллекции, каналы) — сетевые: дашборд Medusa заголовок магазина не шлёт.
  Инварианты товара, категории и коллекции держат хуки workflows Medusa, поэтому они действуют и там.
- Коллекция из дашборда Medusa создаётся без магазина и не видна витринам, пока в её карточке не выбран магазин
  (блок «Магазин», `POST /admin/collections/:id/shop`, один раз). После выбора синхронизация адреса ставит префикс
  handle. Товары в коллекцию списком (`POST /admin/collections/:id/products`) — только её магазина (400).
- `POST /admin/sales-channels/:id/products` закрыт (400): привязка списком обходит хуки товара, а при правиле
  «ровно один канал магазина» может только сломать товар — канал меняется в карточке товара.
- Ограничение менеджеров по магазинам — шаг 43 плана.

## Известные ограничения

- Handle из админки Medusa сначала сохраняется без префикса, префикс ставит подписчик (миллисекунды). В это окно
  тот же handle во втором магазине упрётся в глобальную уникальность Medusa — повторить сохранение.
- Дашборд Medusa показывает товары, категории и коллекции всех магазинов (шаг 43).
